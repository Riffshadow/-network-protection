Задание 1. Разведка системы
Выполненные команды:
bash
Копировать
sudo nmap -sA <ip-адрес>
sudo nmap -sT <ip-адрес>
sudo nmap -sS <ip-адрес>
sudo nmap -sV <ip-адрес>

(Заменить <ip-адрес> на реальный адрес целевой машины)

Результаты сканирования (описательная часть):
TCP Connect Scan (-sT): Установил полное трехэтапное рукопожатие. Менее скрытен, но позволяет определить открытые порты без необходимости прав суперпользователя.
SYN Stealth Scan (-sS): Не завершает сессию TCP, что делает его более тихим и предпочтительным для разведки во многих средах.
ACK Scan (-sA): В первую очередь используется не для поиска открытых портов, а для определения правил межсетевого экрана (stateful/stateless). Если порт помечен как "unfiltered", значит пакет прошел через фильтр.
Service Version Detection (-sV): Определил версии сервисов (например, OpenSSH 8.x), что критически важно для подбора эксплойтов или словарей паролей.

Пример ожидаемого вида записи:

Комментарий к Suricata: Система обнаружения вторжений успешно зафиксировала сетевую активность. Правила сработали по сигнатурам ET SCAN NMAP.

Важно отметить разницу между типами сканирования: например, правило для ACK-сканирования (Nmap Ack Scan) срабатывает иначе, чем для SYN-сканирования.
Suricata видит исходящие пакеты от злоумышленника и определяет их структуру (флаги SYN, FIN, ACK, NULL-пакеты). Поскольку это активная разведка, генерирующая аномальный трафик, IDS классифицирует её как попытку утечки информации (Attempted Information Leak). Однако стоит учитывать риск ложных срабатываний (false positives), если легитимные приложения используют нестандартные паттерны соединений.

Комментарий к Fail2Ban: На этапе чистой разведки (nmap) Fail2Ban не сработал. Это ожидаемое поведение. Fail2Ban анализирует прикладные логи (в данном случае — попытки аутентификации в файле /var/log/auth.log), а не сырые сетевые пакеты. Сканирование портов средствами nmap не оставляет записей об ошибках входа в системном журнале SSH, поэтому триггеры бана отсутствуют. Для защиты от таких сканирований обычно используются другие инструменты (например, встроенные механизмы брандмауэра вроде ufw limit ssh или скрипты типа PortSentry).

Шаг 3. Настройка Fail2Ban

Отредактирован файл конфигурации (предпочтительнее создавать отдельный файл /etc/fail2ban/jail.local, чтобы не затирать настройки при обновлении пакета):

Копировать

enabled = true
port = ssh
logpath = %(sshd_log)s

После сохранения выполнена команда применения настроек: sudo systemctl restart fail2ban

Логи Suricata после начала брута:

Вставьте новые записи из логов.

Пример:

Копировать
08/24/2026-12:10:15.123456 [**] [1:2024894:2] ET SCAN LibSSH Based Frequent SSH Connections Likely Bruteforce Attack [**] [Classification: Attempted Denial of Service] [Priority: 2] {TCP} <IP_АТАКАУЩЕГО>:54321 -> <IP_ЦЕЛИ>:22

Комментарий к Suricata: Suricata обнаружила высокую частоту подключений к порту 22. Сработало правило детектирования попыток подбора учетных данных (Bruteforce). Система идентифицировала аномалию по количеству новых TCP-сессий за единицу времени. Классификация сменилась на Attempted Denial of Service, так как массовый поток запросов может перегрузить службу аутентификации SSH. Стоит отметить ограничение метода: зашифрованный трафик SSH скрывает передаваемые имена пользователей и пароли от анализа содержимого пакетов (DPI), поэтому Suricata опирается исключительно на поведенческий анализ (частоту и тайминги пакетов).

Важное замечание по безопасности: Для реальной инфраструктуры рекомендуется использовать дополнительные меры:

Отключить прямой вход для пользователя root по SSH (PermitRootLogin no).
Использовать беспарольную аутентификацию по ключам.
Вынести SSH на нестандартный порт (security through obscurity).
Настроить географическую блокировку (GeoIP), если доступ нужен только из определенных стран.
