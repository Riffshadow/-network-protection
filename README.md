## Задание 2

### Условие

Проделайте атаку на настройку пароля для службы SSH:

```bash
hydra -L users.txt -P pass.txt <ip-адрес> ssh
```

- **Hydra:** создайте два файла — `users.txt` (имена пользователей) и `pass.txt` (пароли).
- В нашем случае это могут быть случайные строки, но ради эксперимента можно добавить имя и пароль существующего пользователя.
- **Дополнительная информация по Hydra:**  
  [https://kali.tools/?p=1847](https://kali.tools/?p=1847)

#### Включение защиты SSH для Fail2Ban

Откройте файл:

```bash
/etc/fail2ban/jail.conf
```

Найдите секцию:

```ini
[sshd]
```

и установите параметр:

```ini
enabled = true
```

- **Дополнительная информация по Fail2Ban:**  
  [https://putty.org.ru/articles/fail2ban-ssh.html](https://putty.org.ru/articles/fail2ban-ssh.html)

**Результат:** пришлите события, которые появились в логах Suricata и Fail2Ban, прокомментируйте результат.

### Решение

#### Структура стенда 🔗

Атакующая система: **virtualdva (Ubuntu)** с IP-адресом `192.168.56.103`.

Защищённая система: **Practica (Ubuntu)** с IP-адресом `192.168.56.102`.

На защищённой системе установлены:

- IDS/IPS **Suricata**;
- система защиты от перебора паролей **Fail2Ban**.

Обе виртуальные машины находятся в одной подсети **VirtualBox Host-only Adapter**:

```text
192.168.56.0/24
```

---

#### Подготовка словарей ⚙️

На атакующей системе были созданы файлы со списками имён пользователей и паролей.

Содержимое файла `users.txt`:

```text
admin
user
test
ivan
```

Содержимое файла `pass.txt`:

```text
123456
password
qwerty

```

Для проверки содержимого файлов использовались команды:

```bash
cat users.txt
cat pass.txt
```

#### Мониторинг событий защиты 📋

Перед началом атаки на защищённой машине **Practica** были открыты три терминала для наблюдения за реакцией защитной системы.

| Терминал | Команда | Описание |
| --- | --- | --- |
| 1 | `sudo tail -f /var/log/suricata/fast.log` | Просмотр событий системы обнаружения вторжений Suricata |
| 2 | `sudo tail -f /var/log/fail2ban.log` | Просмотр системного журнала Fail2Ban |
| 3 | `watch 'sudo fail2ban-client status sshd'` | Динамический просмотр состояния jail `sshd` и заблокированных IP-адресов |

#### Проведение атаки 🧠

Атака была запущена с виртуальной машины **virtualdva** командой:

```bash
hydra -t 4 -L users.txt -P pass.txt ssh://192.168.56.102
```

> **Важно:** параметр `-t 4` ограничивает количество одновременных соединений до четырёх. Это позволяет SSH-серверу корректнее обрабатывать попытки подключения и записывать события аутентификации в системный журнал.

##### Результат Hydra

В процессе выполнения Hydra могла появляться ошибка:

```text
[ERROR] could not connect to server: Connection refused
```

Ошибка означает, что часть соединений была отклонена SSH-сервером.

OpenSSH имеет собственные механизмы ограничения большого количества одновременных неавторизованных соединений. Поэтому при интенсивном переборе часть подключений может быть сброшена ещё до полноценной попытки аутентификации.

При этом отдельные попытки входа всё равно фиксируются системой и могут использоваться **Fail2Ban** для обнаружения перебора паролей.

---

#### Анализ результатов защиты 🛡️

##### Логи Suricata (`fast.log`)

В журнале Suricata были обнаружены события сетевой активности, например:

```text
[**] [1:2024364:5] ET SCAN Possible Nmap User-Agent Observed ...
{Classification: Web Application Attack} {Priority: 1}
{TCP} 192.168.56.103:57950 -> 192.168.56.102:8080
...
```

**Комментарий:**

Suricata зафиксировала подозрительную сетевую активность между атакующей и защищённой виртуальными машинами.

Поскольку содержимое SSH-сессии передаётся в зашифрованном виде, Suricata не может напрямую увидеть вводимые логины и пароли. IDS анализирует характеристики сетевого трафика и срабатывание установленных правил.

Таким образом, Suricata позволяет обнаруживать подозрительную сетевую активность, связанную с большим количеством соединений и другими признаками потенциальной атаки.

---

##### Логи Fail2Ban (`fail2ban.log`)

Для просмотра журнала Fail2Ban использовалась команда:

```bash
sudo tail -f /var/log/fail2ban.log
```

Также состояние защиты SSH проверялось командой:

```bash
sudo fail2ban-client status sshd
```

В журнале Fail2Ban можно увидеть события обнаружения неудачных попыток авторизации и последующей блокировки IP-адреса атакующей машины.

Пример событий:

```text
fail2ban.filter  [PID]: INFO [sshd] Found 192.168.56.103
fail2ban.actions [PID]: NOTICE [sshd] Ban 192.168.56.103
```

После превышения установленного количества неудачных попыток входа IP-адрес атакующей системы:

```text
192.168.56.103
```

добавляется в список заблокированных адресов.

Таким образом, защитные механизмы успешно обнаруживают и ограничивают попытки перебора пароля SSH.
